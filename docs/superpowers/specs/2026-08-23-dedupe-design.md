# 重複画像の検出・除外 — 設計仕様書

作成日: 2026-08-23

## 背景と課題

処理対象フォルダには同じ画像が複数含まれることがある。電子書籍リーダーのスクリーンショットを
素材にしているため、同じページを二度撮ってしまう、表紙の写真が本文にも再掲される、といった
経緯で重複が生まれる。重複はそのまま出力に流れ込み、抽出結果を水増しする。

### 実測データ

`C:\Users\MANAx2-SUB\Pictures\Images_library_face\raw` 配下の 24 フォルダ（計 2,500 枚超）を
調査した。

| 判定方法 | 結果 |
|----------|------|
| 完全一致（SHA256） | 24 フォルダ中 **2 つだけ**。計 8 枚 |
| 視覚的一致（知覚ハッシュ） | **7 フォルダで各 1〜9 組** |

バイト単位の完全一致は稀で、実態は「視覚的には同じだがバイト列は異なる」重複である。
したがってハッシュ関数には知覚ハッシュ（dHash）が要る。

### 重複には性質の異なる 2 種類がある

目視で 10 組以上を確認した結果、重複は明確に 2 群に分かれた。

| 種類 | 内容 | ハッシュ距離（256bit 中） | 別画像との分離 |
|------|------|--------------------------|----------------|
| **A: 完全に同じ画像** | 同じページを二度スクショした等 | 0〜2 | 明確に分離できる |
| **B: 同じ写真の別バージョン** | 表紙の文字入り版と本文の文字なし版 | 9〜31 以上 | **分離できない** |

B は、タイトル文字が画像の広い面積を覆うためハッシュ距離が大きく開く。実測では距離 27・28・30
のペアがいずれも本物の重複だった一方、その帯には本当に別の写真も混在する。**B を確実に拾える
閾値は存在しない。**

## 設計判断

### 判断1: 判定は余白トリミングの直後に行う

当初は「読み込み直後の元画像で判定する」方針だったが、実測により覆した。

| フォルダ | 判定対象 | 最小距離の上位 12 |
|----------|----------|-------------------|
| 入間ゆい | 元画像 | `2, 3, 4, 4, 5, 6, 6, 7, 7, 7, 7, 8` |
| 入間ゆい | **トリミング後** | `5, 8, 8, 9, 11,` **`53`**`, 57, 58, 59, 60, 65, 77` |
| ちとせよしの | 元画像 | `0, 0, 0, 1, 2, 2, 6, 8, 24, 25, 30, 32` |
| ちとせよしの | **トリミング後** | `0` が 12 組以上 |

`入間ゆい` は 3840×2082 のうち写真が 32% しかなく、元画像のままではハッシュが白余白に支配される。
距離が 2 から連続的に増え、**本物の重複と無関係な画像を分ける境界が消える**。トリミング後は
本物の重複 5 組が距離 5〜11 に固まり、次が 53 に飛ぶ。

余白トリミングは numpy と OpenCV の処理のみで、YOLO や MediaPipe に比べれば桁違いに軽い
（後述の実測で 85ms 対 487ms）。判定位置を 1 段後ろにずらしても高速化の意図は損なわれない。

**余白トリミングが OFF のときも、判定用には内部でトリミングを適用する。**保存される画像は
変わらない。判定の一貫性を保つためである。

### 判断2: dHash は 16×16（256bit）を使う

8×8（64bit）では分離が不足する。

| フォルダ | 8×8 | 16×16 |
|----------|-----|-------|
| 風吹ケイ | 距離 4 以下に 17 組 | 距離 0 に 7 組、次は 25 |
| ちとせよしの | 距離 0 に 5 組、次は 1 | 距離 0 に 3 組、次は 1 |

64bit では偶然の一致が起きやすく、閾値を少しでも上げると誤検出が急増する。256bit では
本物の重複と別画像の間に広い空白が生まれる。

### 判断3: 既定の閾値は 0（完全一致のみ）

種類 B を狙って閾値を上げると別写真を巻き込む。24 フォルダの実測で、距離 0 の誤検出は
ゼロだった。既定は 0 とし、UI から 0〜32 の範囲で調整できるようにする。

この既定では、JPEG の再圧縮やわずかなスクロールずれで距離が 1〜2 になるケース（実測で確認済み）
を取りこぼす。取りこぼしを減らしたい場合は利用者が閾値を上げる。

### 判断4: 残すのは「最初に出会ったもの」

判定は顔検出より前に行うため、「顔が大きく写っているほうを残す」といった選び方はできない。
それを行うには全候補に顔検出が必要になり、高速化の意図が失われる。

走査順（実質ファイル名順）で最初に見つけたものを採用し、以降をスキップする。実装が単純で、
同じ入力に対して常に同じ結果になる（決定的）。

### 判断5: 除外した画像は削除せず退避する

`<保存先>/_duplicates/<入力からの相対パス>` に元ファイルを `shutil.copy2` でコピーする。
入力フォルダには一切書き込まない。誤判定を後から目視で拾い戻せることが、閾値を利用者が
上げられるようにする前提になっている。

### 判断6: 画像を開くのもトリミングも 1 回だけにする

12 枚（2560×1375 前後）での実測値:

| 処理 | 所要 |
|------|------|
| 画像を開くだけ | 12.6 ms/枚 |
| 開く + トリミング + ハッシュ（＝重複判定） | 97.5 ms/枚 |
| 上記 + YOLO + 顔検出 | 584.9 ms/枚 |

重複判定はパイプライン全体の **17%** で、重複を弾ければ **83%** を削減できる。

一方、判定用に画像を開き直すと非重複画像で +15% の無駄が出る。これを避けるため、
`process_spread()` に `preloaded_image` 引数を追加し、判定時に得た画像を下流へ渡す。

## コンポーネント設計

### 新規モジュール `backend/image_hasher.py`

責務は「画像から知覚ハッシュを求め、既出かどうかを判定する」ことのみ。ファイル I/O も
ジョブ状態も持たない。

#### パラメータ

| 定数 | 値 | 意味 |
|------|-----|------|
| `DHASH_SIZE` | 16 | 縮小後の一辺。ハッシュは 16×16 = 256bit |
| `DEFAULT_MAX_DISTANCE` | 0 | 既定の許容ハミング距離（完全一致のみ） |
| `MAX_ALLOWED_DISTANCE` | 32 | UI から指定できる上限。実測の安全域 |

#### `compute_dhash(image: Image.Image) -> np.ndarray`

1. グレースケールに変換し、`(DHASH_SIZE + 1, DHASH_SIZE)` に LANCZOS で縮小する
2. 横方向の隣接画素を比較し、左より右が明るければ True とする
3. 要素数 `DHASH_SIZE * DHASH_SIZE` の 1 次元 bool 配列を返す

整数ではなく bool 配列を返す。numpy でベクトル化して距離を計算するためである。

#### `hamming_distance(a: np.ndarray, b: np.ndarray) -> int`

`int(np.count_nonzero(a != b))` を返す。

#### `class DuplicateIndex`

```python
class DuplicateIndex:
    def __init__(self, max_distance: int = DEFAULT_MAX_DISTANCE) -> None: ...
    def find(self, image_hash: np.ndarray) -> tuple[Path, int] | None: ...
    def add(self, image_hash: np.ndarray, path: Path) -> None: ...
    def __len__(self) -> int: ...
```

- 内部にハッシュを 2 次元 bool 配列（shape: `(n, 256)`）として積み、`find()` は
  `np.count_nonzero(stack != image_hash, axis=1)` で全件との距離を一度に求める
- 距離が `max_distance` 以下のもののうち **最小のもの**の (パス, 距離) を返す。
  同点なら先に登録されたほう（`np.argmin` は最初の最小値を返す）
- 該当がなければ `None`
- 距離も返すのは、退避時のログに「どのファイルの重複で、距離いくつだったか」を
  残すためである

配列は容量を倍々に伸ばして再利用する（追加のたびに積み直さない）。走査枚数が数千に
なると、毎回積み直す実装は O(n²) のメモリコピーになるため。
- `max_distance` が 0 の場合も同じ経路を通す。分岐を増やさないため
- 3,000 枚でも 256bit の比較は numpy で一瞬であり、線形探索で足りる

`max_distance` は `0 <= max_distance <= MAX_ALLOWED_DISTANCE` に丸める。範囲外は
`ValueError` ではなく丸めたうえで警告ログを出す（ジョブを止めないため）。

### `spread_splitter.process_spread()`

引数に `preloaded_image: Image.Image | None = None` を追加する。

渡された場合、その画像は既存の処理フローの **手順 1〜2 を通過済み**とみなし、手順 3 から始める。
渡されなければ従来どおり自分で開く。

`trim_margins` が False のときは手順 2 が何もしないため、呼び出し側は未トリミングの画像を
渡してよい。つまり `preloaded_image` は「トリミング済み」ではなく「手順 2 まで済んでいる」
という意味であり、実際にトリミングされているかは `trim_margins` の値で決まる。

デフォルト `None` により既存の呼び出しとテストは影響を受けない。

### `job_manager`

`_run_job` のループ内、`_process_spread_file` / `_process_single_file` を呼ぶ前に判定段を置く。

```
1. 画像を開く（EXIF 回転・RGB 変換）
2. trim_image_margins() を適用（ハッシュ用。常に実行）
3. compute_dhash() → DuplicateIndex.find()
4. 既出なら _duplicates へ退避し、duplicates を +1 して次のファイルへ
5. 未出なら DuplicateIndex.add()
6. state.trim_margins が True なら手順 2 の結果を、False なら手順 1 の結果を
   preloaded_image として下流へ渡す
```

`state.dedupe` が False のときは手順 1〜6 を丸ごと飛ばし、従来どおりの経路を通る。

判定関数は「重複か」「下流へ渡す画像」に加えて **「その画像が実際にトリミングされたか」**
も返す。通常経路はこの値で「再エンコードして保存するか、バイトコピーで無劣化のまま保存するか」
を決めているため、画像だけを渡すとこの判断ができなくなる。

ただし `trim_margins` が False のときの通常経路（`detect_faces(file_path)` を使う早期分岐）
では、読み込み済み画像を**あえて使わない**。`detect_faces` は EXIF 回転を適用しないのに対し
判定時に読み込んだ画像は適用済みであり、流用すると**重複除外の ON/OFF という無関係な設定で
顔検出結果が変わってしまう**。この経路だけは再読み込み（約 13ms）を許容する。

- `JobState` に `dedupe: bool`、`dedupe_max_distance: int`、`duplicates: int` を追加
- `DuplicateIndex` は `JobState` が保持する（ジョブごとに独立）
- 手順 1〜3 の例外は `logger.error` に記録し、**重複判定をスキップして通常処理に進む**
  （1 枚の失敗でジョブを止めない）

### `image_copier.copy_to_duplicates()`

```python
def copy_to_duplicates(
    src: Path,
    source_root: Path,
    dest_root: Path,
    original: Path,
    distance: int,
) -> Path:
```

`dest_root / "_duplicates" / <src の source_root からの相対パス>` へ `shutil.copy2` する。
中間ディレクトリは自動生成する。ファイル名が重複する場合は既存の `copy_image` と同じく
`{stem}_{連番:03d}{ext}` でリネームする。

`original` と `distance` はログ出力にのみ使う（どのファイルの重複だったかを残すため）。

## API / UI

### Backend

`main.py` の `StartJobRequest` に追加する。

```python
dedupe: bool = False
dedupe_max_distance: int = 0
```

`register_job` → `_pending` → `start_job` → `JobState` へ伝搬する。

完了メッセージ（`type: "complete"`）に `duplicates` フィールドを追加する。
WebSocket のメッセージ型は `progress` / `complete` / `error` の 3 種のまま増やさない。

### Frontend

- `SettingsForm.tsx` に「重複画像を除外する」チェックボックスを追加する
- 詳細設定（`showAdvanced`）の中に許容ハッシュ距離の数値入力（0〜32、既定 0）を置く
- 補足文: 「0 は完全に同じ画像のみを除外します。上げると『表紙の文字入り版』のような
  同一写真の別バージョンも拾いますが、別の写真を誤検出する可能性が上がります。除外された
  画像は保存先の `_duplicates` フォルダに退避されるので、後から確認できます」
- `types.ts` の `CompleteMessage` に `duplicates: number` を追加
- `ResultSummary.tsx` に「重複で除外: N 枚」を表示する

## エラー処理

既存モジュールと同じ方針を踏襲する。

- ハッシュ計算・重複判定の例外は `logger.error(..., exc_info=True)` に記録したうえで、
  重複判定をスキップして通常処理に進む
- 退避先へのコピー失敗は記録して `errors` に計上し、次のファイルへ進む
- 個別ファイルのエラーでジョブ全体を止めない

### 既存動作への影響

既定が `dedupe=False` のため、既存の利用に変化はない。`preloaded_image` もデフォルト `None`
で、渡さなければ従来どおり動く。

### 既知の限界

判定が見開き分割より前にあるため、**分割後に初めて同一になる重複は検出できない**。
たとえば「単ページとして撮った写真」と「見開きの片側として出てきた同じ写真」は、
元画像の形が違うため別物として扱われる。これは判断1で高速化（重複を重い処理の前で弾く）を
優先した結果であり、承知のうえでの割り切りである。

種類 B（表紙の文字入り版と本文の文字なし版）も、既定の閾値 0 では検出されない。
利用者が閾値を上げれば拾えるが、別写真の誤検出と引き換えになる。

### 依存関係

追加なし。`numpy` と `Pillow` は導入済み。
